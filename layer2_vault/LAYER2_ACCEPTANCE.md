# Layer 2: final acceptance table (after the Phase 1-6 improvements)

Status words: **Done** = built and tested here. **Done, with limits** = built and tested, but a stated limit applies. **Not done** = not built. "Tested" means a test in `tests/` passes on SQLite and PostgreSQL unless noted. Phases 1-6 had one independent review round on 20 Nov (three fresh read-only reviewers; findings and fixes in `README.md`, tests in `tests/test_review_findings.py`); it found real defects, all fixed or listed under the limits below. That is one round, not an audit.

Test totals (this machine; 20 Nov, after the independent-review fixes): **263 passed + 10 skipped on SQLite; 273 passed, 0 skipped on PostgreSQL (with a scratch cluster, including the restricted-roles test, which now also runs every app operation as `vault_app` under the tightened grants)**. Earlier totals in this file (224 / 232) are superseded. The 135 tests that existed before the roadmap all still pass. Gateway suite on this vault: 36/37 (the one failure reads the legacy vault's private `_rows`); erasure suite 13/13; legacy vault 24/24.

| Area | Status | Evidence | Remaining limits |
|---|---|---|---|
| Tokenisation | Done | random scoped tokens, per-conversation numbering, same value twice in a request = one token, batched (statements per request independent of value count) - `test_tokeniser`, `test_batching` | token numbers can be reused after a conversation-scope erase (mapping rows are deleted) |
| Encryption | Done, with limits | AES-256-GCM, counter nonces from a durable per-DEK table, `UNIQUE(key_id, nonce)`, exhaustion blocks encryption - `test_crypto_lifecycle` (no reuse, concurrent, restart, rotation, exhaustion) | after restoring an OLD database backup the counter goes backwards; only a random 4-byte epoch makes a repeat unlikely (probabilistic, not proven): rotate DEKs after a restore |
| Key management | Done, with limits | KEK / blind-index / DEK rotation separate; versions identified per key row; revoked versions fail closed; destroyed key cannot be revived (CHECK + trigger); missing master blocks everything | **AWS KMS provider tested only against a fake client**; master secret still in process memory; per-DEK KMS wrapping not built; pre-rotation backups still hold old DEKs |
| Blind index | Done | HMAC with its own key, scoped to borrower + conversation + purpose + type, version dual-read, batch lookups never cross borrowers - `test_blind_index`, `test_batching` | none new |
| Rehydration | Done | deny by default, atomic, uniform denials, expiry enforced on read, scope + purpose + policy via `PermissionEngine` - `test_rehydration`, `test_retention`, `test_api_hardening` | Layer 4 is a stand-in (`PolicyPermissions`), not wired to `layer4_consent` |
| Retention | Done, with limits | expiry fields + migration, cleanup (batched, idempotent, retryable, skips erasure, never destroys a needed DEK), tombstones - `test_retention` (the 8 required tests + more) | **no TTL is set until the policy owner supplies one** (nothing expires by default); EXPIRED mapping rows (no PII) kept to avoid token-number reuse |
| Database | Done, with limits | PostgreSQL pool (health check, timeout, rollback), conversation advisory lock, index review (every hot query uses an index), roles `vault_migration/app/readonly/admin` exercised on a scratch cluster - `test_database_hardening` | local server only (no TLS, replication, managed service); roles SQL not DBA-reviewed |
| Idempotency | Done | `vault_idempotency`: replay, conflict (409), concurrent = one execution, stale recovery, FAILED retry, no PII in rows - `test_database_hardening` | keys expire after a configured TTL (default 24 h, an operational choice) |
| API | Done, with limits | strict schemas, 413 / 422 / 401 / 403 / 409 / 429 / 500 / 503, no leakage in a wide error battery, credential expiry / rotation / revocation, scoped identities - `test_api_hardening`, `test_security_regression` | static bearer tokens (no mTLS/OIDC); 429 throttle is in-memory per process |
| Recovery | Done, with limits | encrypted backups (tamper / wrong key / truncation / reorder rejected), PostgreSQL dump from one cluster restored into another and served, SQLite variant, `RUNBOOK.md` for all eight scenarios - `test_backup_restore` | no scheduling, no point-in-time recovery, backup-key custody is the operator's; **a restore undoes later erasures until replayed** |
| Testing | Done | 224/232 tests; security scan of every table cell, logs, Layer-7 events and error bodies after a full lifecycle, with a negative control that proves the scan can fail - `test_security_regression` | Phase 1-6 code has not had a second-party review; performance measured on one machine |

Performance (measured, `PERFORMANCE.md`): PostgreSQL pooled, local - tokenise 2 new values p50 about 1.0 ms / p99 about 5 ms; 50 values p50 5 ms; rehydrate 1 token p50 0.4 ms; one client about 800-900 req/s; **16 concurrent clients on one process: p99 43-50 ms for tokenisation alone**, so the 50 ms detection + tokenisation budget is not guaranteed under that load.
